## 1. 目标与交付边界

在现有预约、支付闭环之后，增加“到院签到 → 候诊 → 医生接诊 → 就诊完成”。用户继续从“我的 → 我的预约”查看同一条预约，医生通过自己的场次名单操作同一次就诊。

保留一个 Spring Boot 应用、单 Maven 项目和共享数据库，新增 `visit` 业务模块。用户端和医生端是两个使用入口，共用就诊记录。

本期按用户为自己预约理解交互；实现仍以登录账号与预约的归属关系为准，不改变现有就诊人模型。

## 2. 现有能力与新增能力

| 现有能力 | 本期增加 |
| --- | --- |
| 登录、角色、医生档案 | 医生账号关联及 `DOCTOR` 角色 |
| 我的全部预约、预约详情、资料与费用快照 | 就诊时间排序、就诊进度与签到资格 |
| 预约确认时分配就诊序号 | 医生按该序号查看候诊人员、接诊 |

预约快照回答“预约了谁、哪里、哪天、哪个场次”；就诊进度回答“当前进行到哪里”。两部分在同一详情页展示，快照不随进度变化。

## 3. 用户端需求

### 3.1 入口与列表

入口保持“我的 → 个人信息 / 就诊人信息 / 我的预约”。“我的预约”展示当前账号的全部预约，包含原有待支付、取消、过期等记录，不改成只展示已确认预约。

列表及其卡片摘要包含医院、科室、医生、就诊日期、场次时间、就诊序号、当前状态和“查看详情”。卡片摘要可以使用同一次列表响应，无需为中间页面新增接口。

支持按就诊日期、场次开始时间排序：默认 `DESC`，较晚日期在前；可切换 `ASC`。时间相同再按预约 ID 同向排序，保证顺序稳定。这个排序不表示“离现在最近的待就诊预约优先”，也不按预约创建时间排序。

### 3.2 详情与签到

详情继续展示预约快照，增加当前就诊进度、签到时间、开始接诊时间、完成接诊时间和签到按钮。未发生的时间显示“—”。

| 阶段 | 用户展示 | 签到按钮 |
| --- | --- | --- |
| 已确认，尚未到就诊日 | 已预约，待签到 | 禁用 |
| 已确认，就诊当天，尚未签到 | 已预约，待签到 | 启用 |
| 已签到 | 候诊中，展示签到时间和就诊序号 | 禁用，文案可为“已签到” |
| 医生开始接诊 | 就诊中，增加开始时间 | 禁用 |
| 医生完成接诊 | 已就诊，展示完整时间记录 | 禁用 |

签到采用上海时区就诊当天 00:00（含）至次日 00:00（不含）的日期规则，不限制在预约场次内，不增加提前分钟、定位、扫码或现场核验。账号用户到院后自行点击签到，由服务端记录时间。用户不操作开始接诊、完成接诊。

页面进入时查询，签到成功后使用响应更新详情，另提供手动刷新；不要求实时推送。完成后原预约继续保留在“我的预约”，无需新增菜单或拆出独立的“用户就诊看板”入口。

### 3.3 具体正常场景

王小明在 11 月 12 日预约 11 月 13 日李医生上午第一段并完成支付确认，获得就诊序号 003。11 月 12 日详情显示“已预约，待签到”，签到禁用。11 月 13 日 07:50 到院后点击签到，状态进入候诊中；08:15 医生开始接诊，用户查看原详情显示就诊中；08:28 医生完成，原详情显示已就诊及三个时间。

## 4. 医生端需求

### 4.1 身份与场次概览

管理员将已存在的登录账号与已有医生档案一对一关联，并赋予 `DOCTOR` 角色。医生沿用现有登录；授权后重新登录取得含新角色的 JWT。

医生端默认查看今天，可以切换日期。每天按时间顺序展示四个固定场次，包含已确认预约人数、待签到人数、候诊人数、就诊中人数和已就诊人数。没有实际场次或没有预约时展示零，查询不生成场次。

每个场次满足：已确认预约人数 = 待签到 + 候诊中 + 就诊中 + 已就诊人数。

### 4.2 场次人员列表

点击场次后返回该场次全部已确认预约的列表，包含待签到和已就诊记录。每行展示就诊序号、就诊人姓名、当前状态、签到时间以及固定的三个按钮。

列表固定按 `visitNumber` 升序排列，不按签到时间或状态重排；操作或刷新后行顺序保持。号码 1 可以显示为 001。不同医生、日期、场次分别编号，不进行跨场次号码比较。

| 当前进度 | 查看 | 开始接诊 | 完成接诊 |
| --- | --- | --- | --- |
| 待签到 | 启用 | 禁用 | 禁用 |
| 候诊中 | 启用 | 启用 | 禁用 |
| 就诊中 | 启用 | 禁用 | 启用 |
| 已就诊 | 启用 | 禁用 | 禁用 |

三个按钮始终可见，禁用按钮置灰。正常操作时医生完成一位后再接诊下一位；本期按钮仅依据当前行状态，不增加跨行忙碌标记或强制队首选择。医生动作不额外限制为就诊当天或场次时段内，也不由时间任务自动完成。

候诊人员按原号码顺序接诊；未签到者不阻塞已签到者。例如 001 未签到，002、003 已签到，医生可接诊 002。001 后来签到后按原号码参与剩余候诊排序，不影响已经开始的接诊。

### 4.3 查看详情

所有状态均可查看。建议使用只读抽屉或弹窗，关闭后回到当前名单。详情展示：

- 就诊人姓名、证件类型及脱敏证件号。
- 预约单号、就诊序号、日期、场次类型和时间。
- 医院、科室、医生的预约快照。
- 当前就诊状态、签到时间、开始接诊时间、完成接诊时间。

列表不携带完整证件号；详情也不输出完整证件号。本期医生详情不扩展到病历、诊断、处方或支付渠道执行信息。开始和完成操作统一放在列表，详情只读。

进入场次、手动刷新、操作成功后查询最新列表。不增加自动叫号、呼叫状态或推送。

## 5. 状态与业务约定

```mermaid
flowchart LR
    A[已确认预约，待签到] -->|用户签到| B[候诊中]
    B -->|医生开始接诊| C[就诊中]
    C -->|医生完成接诊| D[已就诊]
```

| 就诊进度 | 值 | 产生方式 |
| --- | --- | --- |
| 待签到 | `NOT_CHECKED_IN` | 已确认预约无就诊记录时，查询计算 |
| 候诊中 | `WAITING` | 首次签到创建就诊记录 |
| 就诊中 | `IN_PROGRESS` | 医生开始接诊 |
| 已就诊 | `COMPLETED` | 医生完成接诊，本期终态 |

正常就诊期间预约保持 `CONFIRMED`，支付保持 `PAID`。新进度单独保存，不覆盖预约状态；原有 `workflowStatus` 的预约/支付含义保留。

签到、开始、完成均不释放库存、不重新分配就诊序号、不删除防重复预约占用、不改写快照、不触发退款。`visitNumber` 继续在预约确认时由预约模块分配，不在签到时生成。

其他预约状态不自动解释为待签到。对上线前的记录不推断真实诊疗结果、不批量标记已就诊；新功能验收使用新建预约。

## 6. 范围外

本期只描述正常签到接诊路径。不开发爽约、过号、状态回退、异常恢复新机制、场次结算、自动结束、请假停诊、病历处方、通知、实时推送或真实支付渠道。不新增精确分钟排队时间或预约场次管理能力。

正常权限与状态资格仍是接口业务的一部分：用户操作本人的预约，医生查询和操作自己的预约，管理员负责账号关联。状态不能由客户端任意修改。

## 7. 完成条件

- 用户从原“我的预约”完成查询、签到、查看就诊结果，无需新增菜单。
- 列表按指定就诊时间顺序展示全部预约，原有状态仍可展示。
- 详情中的快照保持一致，签到资格和就诊进度随操作变化。
- 医生四场概览、号码排序、四状态按钮矩阵、全程查看详情符合本文。
- 同一次就诊的用户详情与医生名单状态、时间一致。
- `COMPLETED` 为本期就诊终点，完成后仍可查看记录。
- 原有预约、支付、退款、库存和号码行为通过回归验证。
- 各阶段实测结果另行记录；本文列出的验收标准不是已执行结果。
