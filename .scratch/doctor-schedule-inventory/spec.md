# 医生排班、号源库存与预约暂占：目标业务需求

Status: ready-for-agent

确认日期：2026-10-28。本文记录已与需求提出者逐项确认的**目标业务规则**，供后续设计、实现和验收使用；它不描述当前代码已经具备的能力。项目现有 `docs/api.md`、`docs/business-flow.md` 和 `GLOSSARY.md` 描述的是单号源模型，实施本需求时须同步更新，不能把两种模型混用。

## 一、目标和范围

用户按“医院 → 科室 → 医生 → 日期与上午/下午排班”选择就诊机会。每场医生排班有一个统一的号源库存；用户为当前账号管理的就诊人暂占其中一个名额，限时模拟支付后取得已确认预约和就诊序号。库存竞争只允许实际剩余数量的请求成功，不超卖。

本期覆盖排班配置与放号、库存调整、用户查询与预约、并发暂占、模拟支付、取消与模拟退款、超时释放，以及排班关闭的最低限度处理。既有登录鉴权、就诊人资料、预约快照和账号内创建幂等机制原则上继续保留。

不做普通号/专家号、线上/窗口配额或优先级；所有用户使用同一个池，遵循相同规则。没有真实收款、退款、金额计算或支付/退款失败分支。到院签到、叫号、爽约、诊疗完成、主动通知、自动改约和完整停诊善后不在本期范围内。

## 二、领域对象和数据关系

| 概念 | 业务含义 | 关键规则 |
| --- | --- | --- |
| 医生排班 | 一位医生在指定日期的上午或下午出诊 | 上午固定 `08:00–12:00`，下午固定 `14:00–17:00`；同一医生、日期、时段至多一场。`scheduleId` 标识整场排班。 |
| 号源库存 | 一场排班可同时容纳的预约名额 | 一场排班一个统一池，记录总量、可用量、暂占量、已确认量。 |
| 预约暂占 | 账号为某位就诊人临时保留一个名额 | 对应待支付预约；成功暂占不代表预约最终成立，截止前模拟支付才确认。 |
| 预约凭证 | 预约创建时的医院、科室、医生、排班及就诊人资料快照 | 历史资料不因目录或就诊人资料后来变化而改写；证件号对外脱敏。 |
| 就诊序号 | 已确认预约在同场排班内的相对就诊先后 | 支付确认时按确认顺序发放，单调递增、不复用；它不是库存数，也不承诺精确就诊时刻。 |

开放排班的库存恒等式为：`总名额 = 可用名额 + 暂占名额 + 已确认名额`。取消或过期的历史订单仍保留，但不计入暂占或已确认量。排班关闭后仍可有账面可用名额，只是不得再售；“可用量大于零”不是唯一的预约条件。

账号用户与就诊人的现有关系保持：`patients.user_id` 指向登录用户；一个账号可管理多位就诊人，不同账号也可各自保存同一真实就诊人的资料。预约时只能选择当前账号下已启用的就诊人，`userId` 由登录身份取得，客户端不传。

## 三、排班与放号规则

1. 管理员录入医生、日期、上午或下午及初始总名额。同一医生同一天可以有上午、下午两场，但不能重复创建同一时段；加号须调整既有排班的库存。医生编号用于向用户区分同名医生。
2. 一场排班在就诊日期前第 7 个自然日的 `08:00`（`Asia/Shanghai`）开放。例如 2026-11-08 上午及下午均在 2026-11-01 08:00 开放。开放前不允许预约。
3. 新建暂占在开诊前 30 分钟截止：上午场从就诊日 `07:30` 起、下午场从 `13:30` 起拒绝新预约。恰好到达截止时刻也拒绝；此前已经成功的暂占仍按自身支付截止时间处理。
4. 开放后不得修改医生、就诊日期或上午/下午时段。管理员可以增加总名额和可用名额；减少时只能从当前可用名额中扣除，不能挤掉已暂占或已确认的预约。每次调整记录操作者、时间、变化量和原因。
5. 管理员关闭排班后，不再允许新的暂占；已有待支付预约立即关闭且不能再模拟支付。已确认订单本期不自动取消或退款，用户查询详情时必须看到“医生已停诊，请联系医院”等明确提示。

## 四、用户查询、暂占和防重复

用户先登录并创建或选择就诊人，再查询医院、科室、医生和开放排班。医生展示稳定的 `doctorNo`；排班展示日期、上午/下午、固定起止时间及当前可预约数量。客户端从所选排班取得 `scheduleId`，用户不挑选池中某个具体名额 ID。查询结果仅是当时的快照，提交时后端重新校验。

查询界面应能区分“尚未开放”“可预约”“已约满”“已过预约截止时间”和“排班已关闭”。已约满的排班可以展示为不可选择，而非让用户从列表消失后误认为医生没有出诊；具体接口形状可在实现时确定。成功暂占响应须返回预约单、支付单及支付截止时间；模拟支付成功后的详情须展示就诊序号。已关闭排班的确认凭证须展示停诊提示。

创建请求携带 `scheduleId`、`patientId` 和 UUID `Idempotency-Key`。后端在一个事务中校验账号归属、就诊人启用状态、排班开放窗口与状态、重复预约限制，并原子暂占一个可用名额，再创建预约单、支付单和历史快照。任一步失败则整体回滚。`Idempotency-Key` 仍在账号内唯一；同键同内容重试返回原预约回执，不再次扣库存；取消或过期后发起真正的新预约要使用新键。

“同一就诊人同一场至多一张有效预约”同时按以下两层判断：

- 同一 `patientId` 不能对同一排班持有第二张待支付或已确认预约，即使就诊人资料后来被修改。
- 同一排班下，证件类型与规范化证件号相同的就诊人，即使登记在不同账号下，也不能同时持有两张有效预约。失效的取消、过期订单不阻止再次预约。冲突响应不得暴露其他账号的订单或联系方式。

一个账号可以为不同家人各约一个号。同一真实就诊人可自行选择同一上午的不同医生；系统不限制这种跨排班预约，也不负责判断用户能否赶上两场就诊。

暂占最长 15 分钟。每张预约的支付截止时间为 `min(暂占创建时间 + 15 分钟, 该排班开诊时间)`；当前时间到达截止时即拒绝支付，不存在宽限期。超时关闭由后台处理，扫描可能晚于逻辑截止时间，但支付必须立即失效；释放完成前，页面可能暂时显示较少的可用名额。

## 五、支付、序号、取消与库存流转

| 触发 | 预约单 | 支付单 | 库存变化 | 用户可见结果 |
| --- | --- | --- | --- | --- |
| 成功暂占 | `PENDING_PAYMENT` | `UNPAID` | 可用 −1，暂占 +1 | 暂占成功、显示支付截止时间；尚无就诊序号。 |
| 截止前模拟支付成功 | `CONFIRMED` | `PAID` | 暂占 −1，已确认 +1 | 预约成功，按确认顺序取得就诊序号及凭证。 |
| 待支付时主动取消 | `CANCELLED` | `CLOSED` | 暂占 −1，可用 +1 | 取消成功，无退款。 |
| 待支付超时 | `EXPIRED` | `CLOSED` | 暂占 −1，可用 +1 | 预约过期；之后支付失败。 |
| 已支付且允许自行取消 | `CANCELLED` | `REFUNDED` | 已确认 −1，可用 +1 | 返回“模拟全额退款成功”，保留原就诊序号历史。 |
| 已支付且超过自行取消期限 | 保持 `CONFIRMED` | 保持 `PAID` | 不变 | 返回“距开诊不足24小时，当前不可取消或退款”。 |
| 管理员关闭排班 | 已暂占订单关闭；已确认订单保持原状态 | 待支付单关闭；已支付单保持原状态 | 暂占释放，库存不再对外销售 | 待支付不能继续付款；已确认凭证显示停诊提示。 |

用户自行取消已支付预约仅在 `当前时间 < 开诊时间 − 24 小时` 时允许；恰好到达 24 小时边界即拒绝。即使用户是在开诊前 1 小时刚完成模拟支付，也不享有例外退款窗口。待支付预约可主动取消，不受这条“已支付退款”规则限制；已到支付截止时间但尚未扫描时，取消请求应按过期关闭，不能把它当作按时取消。

“模拟支付”“模拟全额退款”只推进持久化状态并返回结果文字，不发生资金流动、不展示或计算具体金额，也不设计支付或退款失败。所有人收费相同是本期的业务前提；若将来接入真实支付，应另定金额、对账、退款失败与补偿规则，不能把当前 `REFUNDED` 状态解释为真实到账证明。

就诊序号在支付确认时分配，按同一排班的成功确认顺序递增。取消、过期均不复用已经发出的序号。例如容量20且已发到20号，第5号取消后补进一人可取得21号，此时仍最多只有20张有效预约；21号比随后发出的22号先就诊。界面不得显示“第21/20号”或把序号用作剩余号源计算。

库存扣减、重复预约占用、订单创建、支付确认、取消退款及超时释放须分别保证事务原子性。并发请求竞争最后 `x` 个名额时，最多 `x` 个成功；同一订单支付、取消和超时处理竞争时只能产生一种终态，重复请求不能二次扣减或归还库存。

## 六、完整业务场景

### 场景 A：管理员配置并开放

管理员创建“示例市第一人民医院 / 内科 / 张医生 `DOC000001` / 2026-11-08 上午 `08:00–12:00`”，初始总名额20。2026-11-01 08:00 排班开始可预约，库存为 `20 = 20 可用 + 0 暂占 + 0 已确认`。下午 `14:00–17:00` 如需出诊，另建独立排班和库存。

### 场景 B：用户预约与最后三个名额竞争

用户甲登录，创建自己的就诊人资料，选择上述排班。假设此前17个名额已支付确认，此时 `20 = 3 可用 + 0 暂占 + 17 已确认`。20位用户同时提交不同的预约请求，只允许3笔成功暂占；其余17笔显示“暂无号源”。暂占后为 `20 = 0 可用 + 3 暂占 + 17 已确认`。

三名成功用户中：甲在截止前模拟支付，取得第18号；乙主动取消待支付预约；丙15分钟未支付而过期。处理完成后为 `20 = 2 可用 + 0 暂占 + 18 已确认`。乙和丙释放的名额在排班仍可预约时供他人抢号；甲的预约凭证保留创建时的医生、科室、医院、就诊人和上午时段快照。

### 场景 C：跨账号重复与不同医生

母亲、父亲各自账号都登记了同一证件号的孩子。母亲已经为孩子暂占张医生11月8日上午；父亲再选同一排班时被拒绝，不能看到母亲的订单详情。父亲可以为另一位就诊人预约这场排班。孩子如需另约李医生同日上午，系统允许，是否能实际就诊由用户自行判断。

### 场景 D：已确认取消与序号空缺

11月8日上午已发到第20号。持第5号的用户在11月7日08:00**之前**自行取消，系统记录模拟全额退款并释放一个名额；后来用户支付确认后取得第21号，旧第5号不复用。若第5号用户在11月7日08:00或之后才申请取消，则返回“当前不可取消或退款”，原预约与库存均不变。

### 场景 E：临近开诊与排班关闭

11月8日上午从07:30起不再接受新的暂占。07:29成功暂占的用户仍可在其支付截止时间之前完成模拟支付，但截止绝不晚于08:00。若管理员提前关闭排班，则新用户无法预约，待支付暂占立即关闭、不能再付款；已有已确认凭证保留，同时详情显示停诊提示。本期不主动通知、改约或自动退款这些已确认用户。

## 七、验收要点

1. 同一医生、日期、上午/下午不能重复建排班；上午和下午时间固定，开放后关键身份与时间不可改。
2. 放号恰在就诊日前第7个自然日08:00生效；开诊前30分钟起新预约失败，边界时间按 `Asia/Shanghai` 判断。
3. 目录查询展示医生编号、排班时间和可预约数量；客户端提交的是排班 ID，后端仍重新校验。
4. 最后 `x` 个名额的并发请求恰好最多 `x` 笔暂占成功；事务失败后库存和订单不残留半成品。
5. 同一排班的有效预约同时防止同 `patientId` 重复和跨账号同证件重复；取消/过期后允许新键再次预约，不泄露其他账号资料。
6. 暂占成功不发序号；支付成功只确认一次并发放一个不复用的序号。序号允许超过排班总名额。
7. 15分钟或开诊时间到期后支付立即失败；后台重复处理只释放一次，扫描延迟不是付款宽限。
8. 待支付取消、超时、已支付且距开诊超过24小时的取消分别产生正确的订单、支付与库存状态；支付和关闭并发不产生双重终态。
9. 已支付预约到达开诊前24小时边界后不可自行取消或退款；状态不变并返回明确文字。
10. 库存增加、减少仅影响可用部分，调整有操作审计；关闭排班后新预约和待支付付款失败，已确认详情有停诊提示。
11. 模拟支付和退款不触发真实资金操作，不显示金额；历史凭证、幂等回执和本人权限检查继续有效。

## 八、与当前项目的差异及实施注意

- 当前 `schedules` 的每一行是一次独立预约机会，状态在 `AVAILABLE → HELD → BOOKED` 间变化；目标模型中一行排班代表一场上午或下午门诊，`HELD` 与 `BOOKED` 属于单份预约和库存数量，不能继续当作整场排班的状态。现有数据库仅有2099年的三条演示号源，不是目标排班数据。
- 当前没有排班管理和数量库存；已支付预约不能取消，支付单也没有 `REFUNDED`。目录查询、预约创建、支付、取消、过期扫描及 API 文档都需要按目标语义改造。复用 `scheduleId` 字段时须明确其含义变化，不能仅改表结构而保留原校验。
- ADR 0001 的数据库截止时间、只读查询和事务终态原则可保留，但原“预约单 → 支付单 → 单号源”的加锁对象与库存更新方式必须重新设计；ADR 0002 的就诊人快照和账号内 UUID 幂等原则可保留，但需要增加跨账号同证件的有效预约约束。实施时应新增或修订 ADR，明确为何改变原决策，不能静默覆盖。
- 当前迁移 `V1__init_schema.sql` 只面向空库；实施前必须检查实际数据库数据、决定安全的迁移或重建策略，不假设数据库仍为空，也不直接覆盖已有数据。完成后同步更新 `GLOSSARY.md`、`docs/business-flow.md`、`docs/api.md`、HTTP 示例与相关测试。
- 本期的停诊处理有明确业务缺口：已确认用户不会自动获通知、改约或退款。它仅适合当前项目的演示范围；真实医院使用前必须补齐已确认预约的善后流程。
