## 1. 已确认业务规则

使用服务端 `appointmentClock` 的上海业务时间与现有秒精度。以预约单保存的日期、开始和结束时间计算，采用包含开放时刻、不包含截止时刻的区间：

```text
checkInOpensAt  = appointmentDate.atTime(startTime) - 30分钟
checkInClosesAt = appointmentDate.atTime(endTime)
允许首次签到 = 本人预约 && 已确认 && 尚未签到
             && checkInOpensAt <= serverTime < checkInClosesAt
```

| 场次 | 允许签到时间 | 推荐签到时间 |
| --- | --- | --- |
| 08:00–10:00 | [07:30, 10:00) | 07:30–08:00 |
| 10:30–12:00 | [10:00, 12:00) | 10:00–10:30 |
| 14:00–16:00 | [13:30, 16:00) | 13:30–14:00 |
| 16:30–18:00 | [16:00, 18:00) | 16:00–16:30 |

以上均为就诊当天。推荐时间用于提示，开诊后仍在窗口内即可签到。提前30分钟为固定业务规则，本次不增加管理配置。

本规则统一适用于新旧已确认且尚未签到的预约；历史场次按预约快照计算，不以当前场次枚举重建时间。已成功签到的记录不撤销，医生仍按归属、预约已确认及就诊进度开始/完成，无额外的日期或场次时间限制。

未签到且超时的预约继续保持已确认，进度为 `NOT_CHECKED_IN`、`canCheckIn=false`；本次不新增爽约状态，不自动取消、退款、释放库存或删除有效占用。按时签到后医生晚于场次结束接诊仍允许。其他支付、24小时取消、退款、库存、序号和快照规则保持原语义。

## 2. 当前实现与改造位置

| 位置 | 当前事实 | 目标改动 |
| --- | --- | --- |
| `visit.domain.VisitRules` | 仅按确认状态、当天及未签到判定 | 集中计算开放/截止及完整资格 |
| `appointment.application.AppointmentLifecycleCase` | 有日期、startTime，缺少endTime | 追加endTime，由预约快照映射 |
| `DefaultAppointmentLifecycle.view` | 构造稳定预约事实 | 从order.getEndTime映射；同步所有构造点 |
| `visit.application.DefaultVisitService.checkIn` | 读取事实、归属、进度，采样now并插入 | 按共享规则复验窗口，保存同一次采样时间 |
| `bookingquery.application.AppointmentResponseAssembler` | 计算visit及canCheckIn | 同一serverTime计算资格并返回窗口 |
| `appointment.dto.AppointmentVisitResponse` | 五字段record | 追加两个窗口字段 |

继续以VisitRules作为查询与写入共享的纯规则，不读取Clock/数据库，不引入新的策略框架。提供 `checkInOpensAt(date,startTime)`、`checkInClosesAt(date,endTime)`，`canCheckIn` 接收预约状态、日期、起止时刻、进度及完整LocalDateTime。写入口错误分类使用同一组时间计算，禁止在Controller另算窗口。

签到资格以写入口采样时刻判断，不以客户端时间或事务提交时间判断。查询仅代表查询时刻；09:59查询可签到、10:00才提交应失败。现有唯一键继续保护并发首次签到，不为这次规则另加锁或数据库状态。保持现有只读预约事实接口，不跨模块访问Mapper。

无需新迁移、数据库字段、定时任务或新REST路径。现有记录保留首次签到时间，失败请求不写就诊数据，不修改资金或库存。

## 3. 接口与错误契约

继续使用 `POST /api/v1/appointments/{appointmentId}/check-in`，无请求体。按以下优先级判定：

1. 不存在/非本人沿用原错误。
2. 非已确认、已签到或已进入后续进度：沿用4502。
3. now早于开放：新增4503，HTTP409，“尚未到签到开放时间”。
4. now等于或晚于截止：新增4504，HTTP409，“已超过预约场次签到截止时间”。
5. 插入WAITING；并发重复键仍按4502拒绝。

重复签到即使已过截止，也按进度冲突4502处理；次日首次签到为4504。使用现有BusinessException/ErrorCode，不为动态提示扩展全局异常结构。

用户列表与详情的visit追加字段，示例仅说明字段与边界关系：

```json
{
  "status": "NOT_CHECKED_IN",
  "checkedInAt": null,
  "startedAt": null,
  "completedAt": null,
  "canCheckIn": false,
  "checkInOpensAt": "2026-11-13T07:30:00",
  "checkInClosesAt": "2026-11-13T10:00:00"
}
```

仅已确认预约visit非null，含已签到/已完成时仍返回窗口，canCheckIn为false。其他预约继续visit=null。列表统一serverTime；医生DTO本次不追加字段。推荐时段由开放时间至预约开始时间表达，不新增重复字段。
