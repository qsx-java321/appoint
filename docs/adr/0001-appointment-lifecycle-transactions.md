# ADR 0001：预约生命周期采用数据库截止时间与统一事务锁顺序

本文记录最初的同步支付与半日排班设计。ADR 0004 已取代同步支付实现，ADR 0005 已取代当时的日期窗口、支付截止与手工关闭场次规则；当前日期、下单及支付截止以 [ADR 0007](0007-three-day-booking-and-session-cutoffs.md) 为准。数据库截止时间、统一锁顺序、条件更新和库存守恒仍然适用。

## 背景

待支付预约需要支持支付、主动取消和超时关闭。这三条路径会同时修改预约单、支付单和号源，并可能并发执行。本决策形成时尚未接入 RabbitMQ 业务，订单真相保存在 MySQL。

## 决策

- 在预约单持久化 `payment_expires_at`，截止时间取创建后 15 分钟与就诊开始时间中的较早值。
- 使用数据库定时扫描处理到期预约；扫描任务只找候选记录，每张预约由独立事务关闭。
- 支付、取消、过期和排班关闭统一在 `AppointmentLifecycleService` 中处理。自 ADR 0003 起，加锁顺序固定为医生排班、预约单、支付单；创建预约也先锁医生排班，再锁就诊人。
- 库存使用条件更新推进，只有首次把预约从有效状态推进到终态的事务才能释放名额。
- 查询保持只读，通过截止时间计算尚未扫描订单的可操作状态。
- 预约创建时保存就诊对象和时段快照，历史凭证不随目录资料变化。

## 结果

应用重启或扫描重复执行后仍能继续处理未关闭的到期预约；支付、取消、扫描和停诊竞争后，订单与库存保持一种终态。正常情况下后台关闭需等待下一轮扫描；故障或积压时可能更久，但支付截止时间立即生效。未来接入消息队列时，数据库截止时间和事务状态机仍作为最终一致性依据。

## 后续演进

ADR 0004 局部取代“支付、取消、过期和排班关闭全部由 `AppointmentLifecycleService` 同步处理”的决定：目标支付模型改为独立支付模块、异步渠道回调、Transactional Outbox 和 RabbitMQ 事件协调。数据库支付截止时间、排班→预约单→支付单的统一锁顺序、条件更新和库存守恒仍然保留。
