# ADR 0003：预约场次使用统一库存与有效预约占用

> ADR 0005 将新预约场次从上午/下午半日改为四个固定时段，并改为按需生成；本 ADR 的统一库存、有效预约唯一占用、历史兼容和锁顺序继续有效。

`scheduleId` 自 V3 起标识一场门诊，场次保存总量、可用、暂占、已确认和下一就诊序号；数据库检查库存恒等式，并以条件更新和场次行锁串行化同场竞争。有效预约另存一条占用记录，分别以“场次＋就诊人”和“场次＋规范化证件快照”建立唯一约束，从而在保留账号内就诊人关系的同时阻止跨账号重复预约。当时同步生命周期设计按场次、预约单、支付单顺序加锁，避免支付、取消和超时之间形成循环等待；当前异步支付实现的适用范围见下文。

V2 在任何 DDL 前检查旧单号源是否仍有关联的待支付或已确认订单，存在时阻断迁移；V3 只增加列、表、约束和新演示排班，保留旧排班、终态订单和历史快照。旧排班的 `session_type` 为空，因此继续可读但不进入新预约目录，也不参与新库存生命周期。此选择避免清库或改写历史数据，代价是旧模型记录长期以只读兼容形态存在。

## 当前实现适用范围（2026-11-10）

本 ADR 保留 V3 的决策背景。当前 `AppointmentLifecycle.lock` 在内部按场次→预约加锁；取消、过期和对账需要跨模块变更时，再由协调层锁支付父记录。普通支付成功事件确认不重读支付单，支付回调、支付尝试和退款路径只按支付父记录→相关子记录加锁，不反向锁预约。因此不能将原同步流程的三类锁套用于所有当前支付事务。

创建预约自 ADR 0005 起先锁统一设置，再生成/锁定场次并锁就诊人。现行接口与各用例锁序以 [模块设计](../module-design.md#事务与锁序) 为准；迁移门禁“V2 在 DDL 前”特指 V1 之后的 V3 结构升级前，V1 初始化本身仍有 DDL。
