# ADR 0003：预约场次使用统一库存与有效预约占用

**状态** 已接受，部分被取代 · **记录日期** 2026-10-29

> 统一库存、有效占用唯一性及历史兼容仍适用。[ADR 0005](0005-four-session-on-demand-booking.md) 将新场次改为四个固定时段并按需生成。现行锁顺序见[模块设计](../module-design.md#事务与锁序)，现行迁移版本见 [Flyway 基线](../environments.md#flyway初始化基线)。

`scheduleId` 自 V3 起标识一场门诊，场次保存总量、可用、暂占、已确认和下一就诊序号；数据库检查库存恒等式，并以条件更新和场次行锁串行化同场竞争。有效预约另存一条占用记录，分别以“场次＋就诊人”和“场次＋规范化证件快照”建立唯一约束，从而在保留账号内就诊人关系的同时阻止跨账号重复预约。当时同步生命周期设计按场次、预约单、支付单顺序加锁，避免支付、取消和超时之间形成循环等待；当前异步支付实现的适用范围见下文。

## 原迁移链

原 V2 在 V3 结构升级的 DDL 前检查旧单号源是否仍有关联的待支付或已确认订单，存在时阻断迁移。原 V3 只增加列、表、约束和新演示排班，保留旧排班、终态订单和历史快照。旧排班的 `session_type` 为空，因此继续可读但不进入新预约目录，也不参与新库存生命周期。此选择避免清库或改写历史数据，代价是旧模型记录长期以只读兼容形态存在。

## 当前实现适用范围（2026-11-10）

本 ADR 保留 V3 的决策背景。当前 `AppointmentLifecycle.lock` 在内部按场次→预约加锁；取消、过期和对账需要跨模块变更时，再由协调层锁支付父记录。普通支付成功事件确认不重读支付单，支付回调、支付尝试和退款路径只按支付父记录→相关子记录加锁，不反向锁预约。因此不能将原同步流程的三类锁套用于所有当前支付事务。

创建预约自 ADR 0005 起先锁统一设置，再生成或锁定场次，最后锁就诊人。原 V1 初始化本身仍包含 DDL。
