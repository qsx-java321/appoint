# ADR 0002：预约保存就诊人快照，并以账号内幂等键创建

**状态** 已接受 · **记录日期** 2026-10-27

> 就诊人快照和账号内幂等键仍适用。场次标识和摘要字段随 [ADR 0005](0005-four-session-on-demand-booking.md) 更新，现行请求和重放结果见[创建预约 API](../api.md#创建预约)。

## 背景

原创建接口只接收号源，无法说明实际为谁预约；网络重试还可能被当作新的创建请求。就诊人资料允许修改和停用，而预约凭证需要持续反映下单时的信息。

## 决策

账号先维护就诊人，再创建预约。自 ADR 0005 起，新请求使用 `doctorId + appointmentDate + sessionType + patientId`，内部仍关联生成后的 `scheduleId`。预约单复制就诊人的姓名、证件类型、完整证件号码、电话和邮箱；响应只展示脱敏证件号码。历史快照不随就诊人资料变化，也不提供更正入口。

创建请求必须携带 UUID `Idempotency-Key`，键在账号内唯一。自 ADR 0005 起摘要为规范化后的 `doctorId + appointmentDate + sessionType + patientId`；预约关联和首次响应与占号、预约单、支付单在同一事务提交。首次成功返回 HTTP 201 和创建结果；同键同内容重试返回 HTTP 200，以及原预约 ID、预约单号和 `replayed=true` 组成的简短回执，当前状态和支付信息由预约详情提供。相同键配合不同请求返回冲突；失败并回滚的请求不占用键。

首次创建由独立事务服务执行，外层编排在重复键事务退出后读取已经提交的结果。创建先登记账号内幂等请求，再按 ADR 0003 的顺序锁预约场次和就诊人；就诊人修改与启停也锁定同一就诊人行。

预约创建另写入基于创建时证件快照的有效预约占用。同一预约场次中，数据库同时拒绝相同 `patientId` 和相同规范化证件的第二张有效预约；取消或过期时删除占用。

当时按 [ADR 0003](0003-unified-schedule-inventory-and-safe-migration.md) 使用增量迁移承接原 V1 数据。项目后来重新整理了初始结构，当前迁移版本及旧库兼容范围见 [Flyway 基线](../environments.md#flyway初始化基线)。

## 结果

- 预约凭证可以稳定说明实际就诊人和下单时联系方式。
- 客户端可安全使用同一键重试，不会重复占号。
- 重试回执不会把首次创建状态误表示为预约的当前状态。
- 就诊人资料变化与预约创建竞争时，预约获得修改前或修改后的完整快照。
- 跨账号保存同一证件仍然允许，但同一预约场次不能形成两张有效预约。
