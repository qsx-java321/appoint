# 前端页面与交互设计讨论稿

调研日期：2026-11-14（Asia/Shanghai）。状态：讨论稿，现代蓝白方向及首批三张草图已获整体认可，完整页面与视觉细节尚未冻结，不作为新增后端需求。

## 1. 已确认与本轮目标

- 前端采用 Vue 3；此前讨论的 TypeScript、Vite、Vue Router、Pinia 等属于拟采用的配套工具。
- 电脑端优先，同时适配手机浏览器。
- 用户已认可现代蓝白方向及场次选择、预约详情、医生工作台三张草图；本轮继续补齐导航与完整页面设计。
- 本轮调研实际预约产品，讨论页面风格、信息结构和交互，不开发前端业务代码、不修改后端。
- 本轮交付包含参考分析、设计方向及三张可交互草图；尚未冻结高保真视觉稿，未进行真实用户可用性测试。

## 3. 建议的整体方向

定位为多医院预约服务，用户端强调清楚、可靠、容易完成；医生端强调名单扫描和连续操作；管理端强调维护关系与规则影响。三端共用品牌、字体、颜色语义、表单和反馈规范，采用适合各自任务的布局。

| 候选方向 | 视觉与布局 | 取舍 |
| --- | --- | --- |
| 稳重蓝白 | 深蓝标题、白色内容、浅灰底、紧凑的列表、规则提示清楚 | 熟悉、可信；需要通过留白与字体层级避免拥挤 |
| 温和青绿 | 青绿主色、柔和背景、较大的卡片和按钮 | 亲和；状态色要与品牌色区分，文字对比需要检查 |
| 现代蓝白，少量青绿辅助（建议） | 克制的蓝色主按钮、宽松的用户页面、医生和管理端适度增加信息密度 | 兼顾服务感和操作效率，容易在三端保持一致 |

初步设计参数仅供比较：主色可从深蓝 #1768AC 一类方向开始，主背景可用 #F5F7FA，内容面板使用白色；成功、等待、错误使用各自的语义颜色并配文字。关键元素的对比度需在最终配色中验证。

电脑内容区拟约1200px，宽屏设置最大宽度；用户端正文约16px，辅助说明约14px；常用操作高度约40–44px，手机端优先保证足够触控空间。边距按8px倍数组织，圆角约8–12px，浅阴影只用于需要层级的区域。这些是待验证的设计起点。

主要装饰限于小面积品牌图形、图标和空状态。医院与医生资料以实际字段为准：没有照片、医院等级、评分、销量或评价字段时不编造；医生头像可以用姓名首字等中性占位。

## 4. 页面结构

### 4.1 用户端

建议顶部导航为“预约挂号 / 我的预约 / 就诊人”，右侧为账号菜单；个人信息可放入账号菜单，避免增加空泛入口。医生或管理员在具有角色时显示对应工作台入口；沿用统一登录，不在注册页允许自选管理员或医生身份。

预约入口即可承担首页作用：第一屏引导选择医院并进入科室；已登录时可附少量待办提示，但不擅自更改“我的预约”的默认排序。不另建需要填充宣传内容的独立首页。

| 页面 | 核心内容与布局 | 关键交互 |
| --- | --- | --- |
| 登录、注册 | 简洁表单、小面积服务说明；邮箱和密码 | 字段校验、密码可见、提交中状态；401后保留可安全恢复的预约选择 |
| 医院目录 | 医院名称、地址、进入预约；可在已加载目录中按名称筛选 | 选择医院后加载科室；不伪装成全站综合搜索 |
| 医院科室与医生 | 医院摘要、科室选择、当前科室医生列表 | 电脑左侧科室、右侧医生；更换上级清除失效的下级选择 |
| 医生与场次 | 姓名、职称、简介、当前医院科室、三天十二场 | 选一场后再核对；不可预约项保留并说明原因 |
| 预约确认 | 就诊人选择、医院科室医生、日期场次、当前费用、关键取消规则 | 只有明确提交才创建订单；没有就诊人时引导新增，并返回原选择 |
| 支付与结果 | 订单摘要、支付截止、支付操作、处理中和最终结果 | 用创建后详情的金额和截止；受理后查询正式结果，刷新可恢复 |
| 我的预约 | 预约卡片、状态、日期、场次、就诊人、查看详情、排序 | 默认沿用服务端DESC；筛选若仅处理已加载数组应说明范围 |
| 预约详情 | 当前状态、当前动作、预约凭证、支付退款摘要、就诊进度 | 支付、取消、签到按服务端资格；提供手动刷新 |
| 就诊人 | 姓名、脱敏证件、联系方式、启用状态 | 新增、编辑、启停；不提供后端没有的删除动作 |
| 个人信息 | 当前邮箱与角色等已存在资料 | 首版不画没有接口支持的改密、换绑手机和头像上传 |

当前目录也要求登录。默认方案为登录后进入目录；若希望公众先浏览、提交时再登录，需要另行确认并调整后端访问边界。不能仅通过前端隐藏登录提示实现。

### 4.2 医生端

结构建议为顶部“当前日期 + 刷新”，下方四个场次概览，再下方当前场次人员名单。概览可包含每场已确认人数以及待签到、候诊、就诊中、已就诊人数，全部使用现有查询数据。

名单按就诊序号固定升序；行显示号码、姓名、状态、签到时间，以及查看、开始接诊、完成接诊三个按钮。按钮依现有需求保持可见，按行状态禁用；禁用原因可用文字或提示说明。详情使用只读抽屉，关闭后保持日期、场次和滚动位置。

用户操作、日期切换、手动刷新或接诊成功后刷新相应数据。不默认添加实时叫号、预计等候时间、病历处方、患者全局搜索或“必须完成上一位才能接下一位”的额外限制。

### 4.3 管理端

建议菜单为医院科室医生、统一预约设置、医生账号绑定。目录维护可按医院→科室→医生逐级展开，在当前层级使用表格与表单。没有真实统计接口时，直接进入管理内容。

- 删除被引用资源时显示具体错误，不用前端虚构级联删除。
- 设置提交前说明“影响之后首次生成的场次；已有场次和订单保留原设置”。
- 账号绑定当前以已有账号ID操作；不能画出未经支持的全站账号搜索与换绑功能。

## 5. 两个最值得先确认的页面

### 5.1 医生场次选择页

电脑端主区域采用“3个日期列 × 每天4个场次”，让三天选项可以同时比较。每个选项显示日期关联、时间、余号、费用、状态；手机端改为三个日期切换项和当天四个场次卡片。切换日期不自动创建订单。

示意内容不代表实际库存或费用：

| 场次 | 今天 | 明天 | 后天 |
| --- | --- | --- | --- |
| 08:00–10:00 | 已开诊 | 余8号 / ¥10.00 | 余20号 / ¥10.00 |
| 10:30–12:00 | 预约已截止 | 余12号 / ¥10.00 | 余20号 / ¥10.00 |
| 14:00–16:00 | 余3号 / ¥10.00 | 已约满 | 余20号 / ¥10.00 |
| 16:30–18:00 | 余10号 / ¥10.00 | 余16号 / ¥10.00 | 余20号 / ¥10.00 |

确认区在电脑端可放右侧，在手机端放在内容后或底部，始终显示已选日期、场次和“下一步”。仅选中不占号，不显示“已锁定号源”。订单提交后才进入后端暂占与支付期限。

### 5.2 预约详情页

第一块优先回答“现在是什么状态、我要做什么”；第二块展示就诊凭证；第三块展示支付与退款；第四块展示签到与就诊记录。

| 情况 | 建议主文案 | 下一步 |
| --- | --- | --- |
| 待支付 | 请在所示截止时间前完成支付 | 支付或允许的取消 |
| 支付处理中 | 支付正在处理，请稍后查看结果 | 刷新结果，不重复发起活跃尝试 |
| 已收款待确认 | 已支付，正在确认预约 | 查询结果；较长等待时保留单号并提示稍后查看 |
| 已确认未到签到时间 | 预约成功，请在签到窗口内到院签到 | 展示可签到起止时间和场次时间 |
| 已确认可签到 | 到院后可点击签到 | 按后端返回资格展示按钮 |
| 未签到且窗口截止 | 签到时间已结束 | 保留已确认预约事实，不改成爽约或自动退款 |
| 已签到 | 候诊中，您的就诊序号为003 | 手动刷新进度，不估计前方人数或分钟 |
| 接诊中、完成 | 就诊中 / 已就诊 | 查看真实动作时间 |
| 关闭且退款中 | 预约已关闭，退款处理中 | 展示金额和真实退款摘要，不承诺到账日期 |
| 已退回 | 退款已完成 | 保留原预约和退款记录 |

预约关闭原因与资金进度分开表达，例如“预约已过期 · 退款处理中”。不能把所有退款中都解释成用户主动取消。

## 6. 核心交互与边界

- 号源列表是查询快照。提交时若约满或已截止，展示行内提示并刷新当前医生场次；保留医生、就诊人等仍有效的选择，允许改选后再提交。
- 提交时显示处理中、防连续点击；未知结果时保留同一次提交身份，先核实已有订单，避免为了重试制造另一张订单。重新选择内容后的新提交另行处理。
- 预约确认页提示已确认预约只能在距离开诊严格超过24小时时取消。今天、明天的部分场次可能支付确认后即无法取消，规则要在付款前可见。
- 停止新下单时间、现有订单支付截止、签到窗口是三组不同时间，不使用同一个“已过期”标签覆盖。
- 倒计时按服务端时间与持久化截止展示；返回后台后重新获取详情。归零不代表退款或状态已落库。
- 支付模拟仅在开发演示环境提供明确标注的模拟成功/失败操作，不画微信或支付宝扫码图来暗示已接入真实资金渠道。
- 只有异步支付/退款期间考虑有限、可停止的轮询；离开页面停止，长时间处理中给出稍后查看与手动刷新。就诊按既有需求进入页、操作成功和手动刷新更新，不默认增加实时推送。
- 取消确认明确对象、费用和是否进入退款；申请受理后显示“退款处理中”。不写“立即到账”或未经支持的到账天数。
- 就诊人证件响应已脱敏，编辑界面不能将脱敏串作为真实证件号回传；修改证件另行输入，未修改时省略该字段。
- 表单错误放在对应字段旁；加载、无记录、无符合条件数据、网络失败与权限失效分别处理。失败保留输入，清楚给出重试或返回路径。
- 状态用文字配合颜色；所有可操作元素有明确标签、键盘焦点和合理点击区域。关键规则保持可见，不只放在鼠标悬停提示中。
- 返回上一级保持有效选择，切换上级清除失效下级；付款、接诊等成功反馈使用真实响应并重新查询必要内容。

## 7. 对接前需核对的现有契约细节

资料依据：[API](../api.md)、[就诊API](../visit/api.md)、[就诊需求](../visit/requirements.md)、[项目边界](../project-status.md)。

- 现有列表接口以数组为主，不擅自声称已支持服务端全局搜索、状态分页或统计报表。
- 费用和服务端时间以各接口字段为准；确认前所见未生成场次费用可能随统一设置改变，创建后以订单快照为准。
- canPay、canCancel等展示字段和写接口存在已记录差异，尤其已付待确认时canCancel为false但写入口可退款取消。交互冻结前需逐状态核对，首版不在前端自行放宽权限或重写业务规则。
- 医生角色来自JWT；管理员绑定后需要重新登录取得角色。工作台入口展示与服务端实际授权保持一致。
- 就诊序号是场次内确认顺序，不代表精确分钟或实时排队位置。

## 8. 下一轮讨论与设计验收

现代蓝白方向及三张关键页面草图已获整体认可。已继续补齐14个页面模板，导航、页面范围与交互取舍详见[首版导航与完整页面设计稿](frontend-page-scope-and-navigation.md)。下一步围绕完整草图评审信息层级、组件状态和手机重排，随后冻结首版页面范围，再进入Vue实现。

待讨论：

1. 现代蓝白草图的字号、留白和信息密度是否合适；用户端服务感与医生工作台操作效率是否均衡。
2. 预约入口是否直接作为首页；是否保留当前“先登录后浏览”访问方式。
3. 十二场同时展示的电脑布局，是否比“先选日期再看四场”更易理解。

后续可检查的设计完成条件：用户能从界面说明为谁预约、哪家医院哪位医生、哪天哪一场、费用及取消边界；能区分支付中、确认中、已确认和退款中；知道签到窗口及自己的下一步；医生能在不丢失名单位置的前提下完成接诊操作。需用实际原型验证，不把本讨论稿当作已通过可用性验收。

## 9. 2026-11-14 交互草图评审版本

草图在本轮对话内展示，使用虚构医院、人物、号源、金额和示例时间，仅用于页面评审；未创建Vue工程、未接入后端、未提交真实预约或支付。草图包含局部交互脚本，不能作为业务前端已交付的证明。

- 场次选择：电脑上三日期与四场同时展示，旁侧汇总选择；手机切换日期查看四场，摘要放到场次之后。支持选择场次、核对就诊人、查看待支付示例；约满与已开诊不可选。
- 预约详情：顶部突出当前状态与主要动作，下方为就诊凭证、资金信息和就诊进度；提供15种评审状态，覆盖待支付、支付处理、预约确认、签到、接诊、取消、过期及退款。状态切换控件只属于评审工具。
