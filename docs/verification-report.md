## 核心验收

- 在固定上海时钟下验证理论开放时刻包含等号、预约截止时刻排除等号，以及已确认取消恰好到 24 小时边界时被拒绝。
- 20 个不同账号并发竞争容量为 3 的排班，恰好 3 个暂占成功、17 个失败；最终库存为 `3 = 0 可用 + 3 暂占 + 0 已确认`。
- 同一排班同时防止相同 `patientId` 与跨账号同证件重复。首个就诊人修改证件后，旧预约证件快照仍阻止第二个账号以旧证件占用。
- 支付确认按顺序发放 `1、2、3`；取消第 1 号后新确认者取得第 3 号，序号不复用。
- 待支付取消、超时、已确认模拟退款、医院停诊取消分别验证订单、支付单、有效预约占用和库存守恒。
- 验证重复支付、重复取消、幂等键重试、支付与取消竞争、支付与过期竞争、支付与停诊竞争，未发生重复扣减或释放。
- 排班库存增减写入操作审计；普通 `USER` 调用管理员接口返回 403。

## 迁移验证

`InitialSchemaMigrationTest` 从独立 V1 库插入旧 `PENDING_PAYMENT` 订单后执行完整迁移，V2 按预期阻断，且 V3 的 `session_type` 列尚未出现。无旧有效订单时，空库顺序执行 V1、V2、V3；第二次执行不重复迁移。MySQL 8.4 隔离容器也成功执行全部三版迁移。

本地 Compose 数据库在迁移前为 V1：排班 3，用户、就诊人、预约单和支付单均为 0。迁移前逻辑备份保存为 `/tmp/appoint-pre-v3-20261029.sql`，大小 16,843 字节，SHA-256 为 `96698fd0955a4baee5754d4a18f09e4ef7419ca1886d16b8ebacf3c1be515108`。

Flyway 随后只执行 V2、V3。迁移后 schema 为 V3：排班 5，其中 3 条旧单号源原样保留、2 条为新模型排班；用户、就诊人、预约单、支付单和有效预约占用仍均为 0。统一库存恒等式异常行数为 0。迁移过程中没有删除数据库、数据卷或已有行。

## 仍未覆盖的业务边界

- 没有真实支付、金额、对账、退款失败或补偿。
- 没有自动通知、改约、签到、叫号、爽约和诊疗完成。
- 排班关闭后已确认预约只保留并显示停诊提示；不会自动退款或安排替代医生。
- 只支持居民身份证；不校验证件与操作账号的现实归属。
- 同一就诊人预约不同排班不受限制，系统不判断时间冲突。
- 开诊后的停诊处理未实现。
- Flyway 运行时会提示当前依赖声明验证到 MySQL 8.1；本轮已在 MySQL 8.4 实际通过迁移和集成测试。
